# Aeolus v0.5 Plan (plan of record)

The v0.4 plan (`AEOLUS_V0.4.md`) shipped in 0.4.0. This document is the
v0.5 plan of record; every `v0.5 §X` citation in code and reports refers
here.

Goal: **close every follow-up the reports name that is doable in-repo.**
Two threads remain open after 0.4.0, both documented, neither upstream-
blocked: the benchmark report's allocation counters (report 08 — "or the
project writes its own global allocator counting harness", deliberately
out of scope for v0.4) and the element-relative typography gap (v0.4
§2.3 kept `tracking-*` / bare `leading-*` out of the corpus because the
IR resolved them at the 16px base). v0.5 ships both: the plan IR gains
element-relative text values carried as RELATIVE units, the golden
corpus pins them against the real compiler, and a counting global
allocator turns report 08's structural claims into measured contracts.
No backend manifest changes, no MSRV bump; the four upstream-blocked
deferrals (v0.4 §6) stay deferred and are re-documented in §5.

## §1 — Element-relative typography (reverses the v0.4 §2.3 exclusion)

- §1.1 The IR carries the relative unit the class NAMES, not a 16px
  pre-multiplication: `TextValue::TrackingEm(f32)` (letter-spacing in em,
  the `--tracking-*` token form) and `TextValue::LineHeightRatio(f32)`
  (unitless line-height, the `--leading-*` token form). Absolute forms
  stay exactly as they are: `TextValue::Px` for `leading-[13px]`,
  `tracking-[7px]`, the spacing-multiple modifiers (`text-sm/6` =
  `calc(var(--spacing) * 6)`) and `underline-offset-*`; `TextValue::Spacing`
  stays for arbitrary px letter-spacing. Additive enum variants (the
  v0.3 §2.2 precedent; 0.x minor bump, documented in the changelog).
- §1.2 Resolution: `tracking-{tighter..widest}` resolves to the token em
  (v4.1.17 `--tracking-*`: −0.05 … 0.1em), the `negative` flag now
  applies to the token arm (v4's negative-utility marker negates the
  token value); bare `leading-{token}` resolves to the `--leading-*`
  ratio (`--leading-none` = 1 …); `text-{size}/{named-leading}` resolves
  to the ratio (v4 emits `var(--leading-tight)` — unitless), while
  `text-{size}/{number}` stays absolute (v4 emits `calc(var(--spacing) *
  n)`). The paired line-height of a bare `text-{size}` stays token-
  resolved absolute px (v0.4 behavior, corpus-pinned): the pairing is
  part of the size token itself, not an element-relative value.
- §1.3 The verification emitter (css.rs) emits v4's relative shapes:
  `line-height: 1.25` (unitless) and `letter-spacing: -0.025em`. Px
  forms are unchanged. Because BOTH sides of the corpus carry the same
  relative text, parity is pinned exactly — the harness needs no new
  normalization for these families (the existing unitless-line-height ×
  same-rule font-size normalization already covers the `text-*/*`
  entries where a font-size is declared in the same rule).
- §1.4 Backends: Floem lowers `LineHeightRatio` to
  `LineHeightValue::Normal(ratio)` — Floem's NATIVE font-size-relative
  form (the capability matrix row upgrades from absolute-pt to
  element-relative); `TrackingEm` keeps the honest drop report (no
  letter-spacing property at the pinned Floem rev). The Masonry fallback
  applies no text properties today (the parley per-widget gap, Q5) —
  unchanged and still reported.
- §1.5 `cn()` conflict groups are unchanged (`leading-*` → line-height,
  `tracking-*` → letter-spacing; a ratio and a px leading in the same
  string are the same group, later wins — value shape is not part of the
  key, matching tw_merge).
- §1.6 Element-level composition — WHICH font-size multiplies an em or
  ratio — is the renderer's cascade duty (CSS `em` semantics, Floem
  resolves the multiplier at paint). The plan records this in the
  `TextValue` docs; the corpus pins the relative units, not a font-size
  the compiler cannot know.

## §2 — The corpus grows (`tools/gen_golden.mjs`)

- §2.1 New entries, generated by the REAL tailwindcss 4.1.17: the six
  `tracking-*` tokens, the negative form (`-tracking-wide` — v4 emits
  the negated token), arbitrary absolute forms (`tracking-[7px]`,
  `leading-[3px]`), the six named `leading-*` tokens plus
  `leading-none`, and the named-modifier text sizes (`text-base/tight`,
  `text-lg/loose`) alongside the existing absolute `text-sm/6`. A small
  shadcn-theme batch (`tracking-normal`, `leading-relaxed`) pins theme-
  context independence.
- §2.2 Every new entry must resolve with ZERO warnings (the coverage-
  guard contract, unchanged) — `tracking-*`/`leading-*` already resolve,
  so the corpus upgrade is a semantics change, not a coverage change.
- §2.3 The v0.4 §2.3 scope note is REWRITTEN, not deleted: element-
  relative values ARE now corpus-pinned — as the relative units the plan
  carries (§1.6); what stays out is still out for the same reason
  (element-resolved composition), now documented as a model boundary
  instead of a corpus gap.

## §3 — The allocation contract (`tests/alloc_contract.rs`, report 08)

- §3.1 A counting global allocator (`std::alloc::GlobalAlloc` over
  `System`, two `AtomicU64`s, a tracking gate) in the test binary —
  zero new dependencies; aeolus-core stays zero-dep even in dev-deps.
- §3.2 The harness exposes a `measured(|| …) -> (allocs, bytes, ret)`
  serialized by a mutex (tests in one binary share the allocator);
  divan 0.1.21 cannot carry per-benchmark allocation counters (its
  `IntoCounter` is a fixed per-iteration value, not a sampled delta —
  re-verified and documented), so the contract test IS the deliverable
  the report asked for.
- §3.3 The contract pins report 08's structural claims as measured
  numbers: `diff` of equal plans allocates ZERO (pinned exactly); the
  intern hit path and the warm cache hit are pinned as upper bounds with
  the measured numbers recorded (clone-shaped allocations churn across
  rustc versions — bounds, not exact pins); `cn()` on the 33-class
  Button merge and the cold resolve are counted for the report.
- §3.4 Report 08 gains an allocation table and CLOSES the follow-up:
  the divan re-test outcome (§3.2) is documented honestly next to the
  numbers.
